# uncertainty — 모르면 반드시 먼저 물어본다

## 핵심 규칙
- **"계획/문서에 적힌 내용"과 "실제로 확인된 현황"을 항상 구분한다.** 문서(`docs/`, `tasks/handoffs/` 등)에 적혀 있어도, 그것이 실제 상태와 일치한다고 확인되지 않았으면 "계획상으로는 ~"이라고 명시하고 단정하지 않는다.
- 아래에 해당하면 **답변/작업 전에 반드시 사용자에게 먼저 질문한다** (임의로 추측하거나 문서 내용으로 대신 답하지 않는다):
  - 실제 배포·운영 상태를 묻는 질문 (예: 실서버 DB 설정, 실제 저장된 데이터, 지금 무엇이 돌아가고 있는지)
  - 문서에 `TBD`/`미정`/`확인 필요`로 표시된 값이 이번 작업에 필요할 때
  - 코드/설정 파일이 실제로 존재하는지 불확실할 때 — 먼저 Glob/Read로 확인하고, 그래도 불명확하면 질문
  - 여러 해석이 가능한 요구사항 (기존 "애매하면 물어본다" 규칙과 동일선상)
- 확인 안 된 사실을 근거로 결론을 내리거나 다음 작업을 진행하지 않는다. "모른다"고 말하는 것이 틀린 추측보다 항상 낫다.
- **에이전트가 제안한 값(권장안, ✅ 권장)은 사실이 아니다.** 사용자가 실제로 답변한 것(답변 완료:)과 다르다. [[.claude/rules/core/open-questions.md]] "🚨 절대 규칙: 권장안과 답변 완료는 다르다" 섹션 참고. 권장안만 본 후 그것을 마치 확정된 사실처럼 다루지 말 것 — "XX의 권장안은 있지만, 사용자 답변이 없다"고 명시해야 한다.
- 발견한 확인 필요 사항은 즉석 질문으로 끝내지 않고 `tasks/questions/open-questions.md`에 큐로 기록한다 (절차: [[.claude/rules/core/open-questions.md]]).

## Why
사용자가 "지금 실제로 어떻게 돌아가고 있나"를 물었을 때, 확인된 사실이 없는데도 문서(계획)에 적힌 내용을 근거로 답해버리는 사고가 실제로 있었다. 사용자가 매번 "이거 진짜 아는거 맞아?"라고 되물어야 한다면 신뢰가 깨진다.

또 다른 사고: 어떤 문서의 "확정 필요" 항목을, 사용자 답변이 아니라 `open-questions.md`의 에이전트 권장안(✅)만 보고 "확정됨"으로 잘못 바꾼 적이 있다. 사용자가 직접 지적한 뒤에야 발견해 원복했다 — 권장안과 실제 답변을 구분하지 못하면 존재하지 않는 사용자 결정을 지어내는 것과 같다.
