# open-questions — 확인 필요 사항 큐 관리

## 배경
[[.claude/rules/core/uncertainty.md]]에 따라 확인되지 않은 사실은 임의로 답하거나 진행하지 않고 사용자에게 먼저 물어봐야 한다.
매번 대화 중간에 즉석으로 물어보고 흘려보내는 대신, 발견 즉시 `tasks/questions/open-questions.md`에 기록해 큐로 관리한다 — 대화/세션이 끊겨도 무엇을 확인해야 하는지 잊지 않기 위함.

## 규칙
0. **우선순위: 기반 환경 확인이 세부 사항 확인보다 먼저다.** "무엇을 어떻게 굴릴 것인가"(어디에 무엇이 있는지, 무엇을 이미 쓰고 있는지, 누가 무엇을 담당하는지)를 세부 질문(개별 항목의 형식·저장 위치 등)보다 먼저 정리하고 먼저 묻는다. 기반이 안 정해지면 세부를 정해도 나중에 다 뒤집힌다.
   `tasks/questions/open-questions.md`는 아래 섹션 순서를 유지한다:
   `0. 먼저 답해주세요(선행)` → `A. 인프라·운영` → `B. 업무 프로세스` → `C. 범위·데이터`
   이 업종에서 위 3개로 부족하면 섹션을 추가해도 되지만, "선행 질문이 맨 위"라는 순서 원칙은 유지한다.
1. 작업 중 확인 안 된 사실(TBD, 애매한 요구사항, 실제 현황 불명 등)을 발견하면:
   - `tasks/questions/open-questions.md`에 새 항목을 append한다 (아래 형식).
   - 같은 응답 안에서 사용자에게도 질문 내용을 알린다 (파일에만 적고 조용히 넘어가지 않는다).
1.5. **질문을 다시 던지지 않았는데 사용자가 대화 중 관련 사실을 확정/실행한 경우도 "답변"으로 취급한다.** (실제로 있었던 사고 재발 방지 — 에이전트가 다시 묻지 않았는데 사용자가 대화 중 어떤 결정을 이미 실행까지 마쳤는데도, open-questions.md의 관련 항목이 갱신되지 않은 채 그대로 남아있었던 사례가 있었다)
   작업을 계속 진행하기 전에, 지금 하려는/방금 마친 작업이 open-questions.md의 미답변 항목과 같은 주제를 다루는지 먼저 확인한다. 같은 주제면:
   - 이번 결정/실행으로 그 항목이 해소됐는지 판단한다.
   - 해소됐으면 **즉시**(다른 작업으로 넘어가기 전에, 나중으로 미루지 않고) 아래 2번 절차(삭제/축소 + 원본 문서 반영)를 그대로 따른다.
   - 애매하면 사용자에게 "이게 Q{n}의 답으로 확정된 걸로 볼까요?"라고 확인 후 반영한다.
2. 사용자가 답변하면:
   - 질문이 **완전히 해소**됐으면(후속 파생 질문이 없으면) `open-questions.md`에서 **삭제**한다 (완료 표시만 하고 남겨두지 않는다).
   - 답변으로 **일부만 확정**되고 같은 항목 안에 여전히 미답 세부 질문이 남으면, 삭제하지 않고 **"답변 완료: {확정된 내용}"**을 항목 안에 추가한 뒤 잔여 질문만 남기고 축소한다. 이 경우도 확정된 부분은 반드시 원본 문서에 즉시 반영한다 — 항목을 남겨뒀다고 반영을 미루지 않는다.
   - 답변 내용을 원본 문서에 반영한다 (그 사실을 "원본으로 담는 문서"가 어디인지는 이 vault의 문서 구성에 따라 정한다 — 같은 사실을 두 문서에 각각 적으면 나중에 어긋난다). 반영 시 그 문서에 이미 있는 동일 항목의 기존 표기(대소문자, 날짜 형식 등)와 충돌하지 않는지 대조 후 적는다.
3. 항목 형식:
   ```
   ### Q{n} — {제목}  [지금 필요 | {기능} 착수 시]
   - 배경: 어느 문서의 어떤 공백/모순에서 나왔는지
   - 경우의 수:
     a. {선택지} — {장단점}
     b. {선택지} — {장단점}
   - ✅ 권장: {안} ({근거})
   - 막고 있는 것: 이 답이 없으면 진행 못 하는 작업
   - 반영 대상: {문서 경로}
   ```
   - **권장안을 반드시 붙인다.** 사용자가 "권장안대로 가자"만 답해도 진행 가능해야 한다. 근거는 이 프로젝트의 고정 제약({{도메인_제약}})에 맞춘다.
   - 단 **사실 확인 항목**(실물 보유 여부, 예산, 팀 구성 등)은 추측하면 안 되므로 `✅ 권장: 없음 (사실 확인 항목)`으로 명시한다 ([[.claude/rules/core/uncertainty.md]]).
   - 번호(Q{n})는 삭제된 번호를 재사용하지 않고 계속 증가시킨다 (단순 식별자).
   - 다른 질문의 답을 봉쇄하는 **선행 질문**은 문서 맨 위 "0. 먼저 답해주세요" 섹션에 표로 모아 답변 우선순위를 제시한다.
4. 세션을 새로 시작할 때 이 파일에 항목이 남아있으면, 다른 작업보다 먼저 사용자에게 안내한다.
5. 폴더 신설 규칙([[.claude/rules/core/file-ops.md]])에 따라 `tasks/questions/README.md`에 관리 파일 목록을 유지한다.

## 🚨 절대 규칙: 권장안(✅)과 답변 완료(답변 완료:)는 다르다

**절대 혼동 금지.** 이 프레임워크에서 가장 자주 나는 사고다.

| 구분 | 표기법 | 의미 | 사실로 쓸 수 있는가? |
|---|---|---|---|
| **권장안** | `✅ 권장: {안} ({근거})` | 에이전트가 제안한 것. 사용자가 아직 승인하지 않음 | ❌ **아니오. 이것만으로는 사실이 아니다** |
| **답변 완료** | `**답변 완료**: {사용자가 입력한 실제 값}` | 사용자가 **실제로 답변한 것**. 확정된 사실 | ✅ **가능. 원본 문서에 반영한다** |

**적용 규칙:**
- 어떤 문서에 "XXX 확정 필요"라고 적혀 있으면, 그건 아직 확정되지 않은 것이다. open-questions.md에 권장안(✅)만 있는 상태일 수 있다.
- 권장안을 본 후 "사용자가 이것에 동의했다"고 임의로 판단하고 다른 문서를 "확정됨"으로 바꾸면 안 된다.
- 어떤 문서든 "확정 필요"를 "확정됨"으로 바꾸려면 **반드시** open-questions.md에 `**답변 완료**: ...` 표기가 있어야 한다. 그 표기를 보지 못했으면 사용자에게 먼저 확인한다.
- 의심스러우면: 그 사실을 담는 원본 문서에 값이 이미 기록되어 있는가? → 기록되어 있으면 확정된 것. 없으면 미확정.

**체크리스트 (매번 확인):**
1. "확정 필요"로 표기된 항목을 수정하려 할 때: open-questions.md에서 해당 Q번호를 grep해서 `**답변 완료**:` 줄이 있는지 확인한다.
2. 없으면? → 사용자에게 질문하거나, 권장안일 뿐이라고 명시하고 진행하지 않는다.
3. 권장안을 근거로 다른 문서를 고치면 안 된다.

## 작업 완료 시 자가 대조

어떤 작업(코드 구현이든, 인프라 설정이든, 문서 작성이든)을 마칠 때, 그 작업이 open-questions.md의 미답변 항목 중 하나를 실질적으로 답했는지 훑어본다. 검색 방법: 방금 확정한 핵심 키워드(예: "저장소", "private", "2개 분리")로 `tasks/questions/open-questions.md`를 grep한 뒤, 관련 항목이 있으면 위 규칙 1.5를 따른다.

이 대조는 `verify-docs` 재검증과 다르다 — verify-docs는 **이미 문서화된 텍스트끼리** 비교하고, 이 대조는 "방금 한 행동"과 "아직 텍스트화 안 된 결정 여부"를 비교한다. 후자는 기계 검증 대상이 아니므로(비교할 텍스트가 애초에 없음) 매번 사람(에이전트)이 직접 확인해야 한다.

## 재검증 대상 문서 목록 (고정)

아래 목록은 `open-questions.md`와 같은 사실(Q번호, 확정/미확정 여부)을 언급하는 vault 내 전체 문서다. 이 표는 `Q[0-9]|open-questions` 정규식으로 vault 전체를 grep해서 만든다 — 재검증할 때마다 이 표만 순회하면 되고, 표에 없는 문서는 검증 대상에서 제외해도 된다. **매번 즉흥적으로 검증 범위를 넓혀가다 같은 파일을 반복해서 놓치는 실수**를 막기 위한 장치다.

| 문서 | 이 문서가 담는 것 |
|---|---|
| `tasks/questions/open-questions.md` | 원본 큐 |
| `log.md` | 작업 로그 — 과거 Q번호 인용이 남아있을 수 있음. 로그는 과거 시점 기록이므로 값 자체를 고치지 않되, 이번에 반영한 변경 사항을 새 줄로 추가했는지 확인 |

이 업종/프로젝트에서 실무 원본 문서(예: 환경설정, 제품 기획, 팀 운영 규칙)를 새로 만들면,
그 문서가 Q번호나 "확정"류 표현을 담게 되는 순간 이 표에 먼저 추가한다. 표에 추가하지
않고 방치하면 `verify-docs` 스크립트가 `[list]`로 잡아낸다.

## 답변 반영 후 재검증

한 번에 여러 항목(2개 이상)을 반영하는 작업을 마쳤으면, **일괄 반영이 끝난 시점에 한 번**(항목마다가 아니라 배치 단위로) `verify-docs` 스킬을 실행한다. 실제 모순은 여러 항목이 동시에 바뀔 때 생기기 쉽고, 매 항목마다 전체를 재검사하면 토큰 낭비이기 때문이다.

```bash
python .claude/skills/verify-docs/check.py
```

**절차 상세는 스킬이 갖는다** (`.claude/skills/verify-docs/SKILL.md`) — 이 규칙 파일에 같은 절차를 중복 서술하면 둘이 어긋나므로, 여기에는 "언제 실행하는가"만 둔다.

- 위 "재검증 대상 문서 목록" 표는 스킬 스크립트가 읽는 **기계용 데이터**이기도 하다. 표를 고칠 때 표 형식(`| \`경로\` | 설명 |`)을 유지한다.
- 스크립트는 dangling 참조·요약 불일치·표 누락을 잡고, 의미적 모순(두 문서가 같은 사실을 다르게 서술)은 스킬 3단계의 사람 판단에 맡긴다. 100% 자동 보장이 아니다.
